# Context: Phase 1.2 - Secure Proxy Gateway

## Domain
Implementation of a secure, granular, and performant gateway on Vercel to bridge the frontend with the GitHub Actions backend. This phase specifically resolves the CORS preflight deadlock and ALPN negotiation failures.

## Decisions

### 1. Granular Serverless Architecture (Option B)
- **Pattern**: File-based routing in the `/api` directory for better maintainability and debugging logs.
- **Endpoints**:
    - `/api/session.ts`: Handles authentication handshakes.
    - `/api/market.ts`: Handles market data requests (candles, etc.).
    - `/api/order.ts`: Handles order execution and management.
- **Implementation**: Each function uses `undici` with a forced HTTP/1.1 agent (`allowH2: false`) to resolve the ALPN failures encountered with Cloudflare Tunnels.

### 2. Tiered Secret Ownership
- **Vercel Layer**: Stores infrastructure secrets (`CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET`) as Environment Variables.
- **GitHub Actions Layer**: Stores trading secrets (`CAPITAL_USER`, `CAPITAL_PASSWORD`, `CAPITAL_API_KEY`).
- **Result**: Tokens are injected server-side by Vercel; the browser never sees infrastructure secrets. Trading credentials remain isolated in the execution backend.

### 3. Frontend Decoupling
- **Pathing**: The frontend will use relative paths (`/api/...`) exclusively.
- **Header Injection**: All `CF-Access` header injection logic is removed from the browser-side `src/api/client.ts`.
- **Local Dev**: Local proxying in `vite.config.ts` is abandoned in favor of a direct Vercel-first deployment workflow.

### 4. Performance & Reliability
- **Client**: `undici` is selected as the fetch client for the serverless functions due to its performance characteristics and low-level TLS/ALPN control.
- **Handshake**: The proxy will pass through Capital.com tokens (`CST`, `X-SECURITY-TOKEN`) transparently to maintain the session state managed by the frontend.
