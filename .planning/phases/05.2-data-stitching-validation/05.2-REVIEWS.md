# Cross-AI Plan Review — Phase 5.2

## Gemini Review

### Summary
The plan provides a strong, well-structured approach to validating the Market Data Engine. It accurately targets all key decisions outlined in the research phase (D-01 through D-05), including gap tolerance, reconnection resilience, environment switching, and subscription leaks. The instructions are specific and trace directly back to the project requirements. However, strictly adhering to the "no local mocks" rule while simultaneously attempting to test precise timing thresholds (e.g., a >1s data gap) introduces a significant risk of test flakiness in a live environment. 

### Strengths
- **Clear Traceability:** Tasks map perfectly to the required scenarios (D-01 to D-04) and strictly adhere to the testing directives (D-05).
- **Thorough Reconnection Scenarios:** Task 2 properly differentiates between client-side WebSocket drops and server-side disconnects via the Vercel proxy.
- **Watchlist Nuance Handled:** Task 4 explicitly accounts for the reference-counting edge case, stipulating the use of non-watchlist symbols to accurately test for memory/subscription leaks.
- **UI State Validation:** Task 3 correctly validates that old data remains visible until seamlessly overwritten during environment switching, focusing on user experience rather than just network state.

### Concerns
- **HIGH — Test Flakiness (Task 1):** Asserting that a `DataStitchingError` is thrown when a gap is `>1s` on a live endpoint is highly non-deterministic. Without using Playwright's network interception to artificially delay the live REST response, this test will either be impossible to trigger reliably or will randomly fail in CI due to natural network latency.
- **MEDIUM — Error Handling Clarification (Task 1):** The plan requires verifying that `DataStitchingError` is thrown, but it doesn't specify the expected app behavior afterward. Does the app crash? Does it retry the REST fetch? The test should assert the app's recovery mechanism, not just the presence of the error.
- **LOW — Live Credentials (Task 3):** Toggling to the Live environment will require valid live credentials (`cst` and `securityToken`). The plan doesn't mention how these will be securely injected or mocked for the E2E test environment.
- **LOW — File Bloat:** Placing data stitching, complex reconnection logic, environment switching, and leak tracking all in a single file (`tests/e2e/market-data-stitching.spec.ts`) may make the test suite difficult to maintain. 

### Suggestions
- **Induce Artificial Latency:** Update Task 1 to explicitly use Playwright network interception (e.g., `route.continue` with a simulated delay) on the REST endpoint to deterministically induce the `>1s` gap, while still hitting the live backend.
- **Define Recovery Expectations:** Clarify in Task 1 how the UI should behave when the `DataStitchingError` is thrown (e.g., showing a loading spinner while it refetches data) and assert that behavior.
- **Handle Live Credentials:** Add a note in Task 3 ensuring that the test environment is provisioned with valid Live API credentials, or define a strategy for bypassing the authentication gate for this specific test.
- **Split Test Files:** Consider splitting the implementation into `market-data-stitching.spec.ts` (Tasks 1 & 4) and `market-data-resilience.spec.ts` (Tasks 2 & 3) to improve test organization.

### Risk Assessment
**MEDIUM.** The core logic and coverage of the plan are excellent. The primary risk lies in test reliability. E2E tests against live endpoints are inherently flaky, and testing precise network timing conditions without deterministic interception will likely result in a brittle CI pipeline. Implementing artificial network delays via Playwright will reduce this risk to LOW.

## Codex Review

### 1. Summary
The plan for Phase 5.2 is extremely focused, well-structured, and directly aligns with the phase's context and research documents. It effectively translates the five key architectural decisions (D-01 through D-05) into actionable Playwright E2E tasks without deviating into out-of-scope territory. The approach to test against the live environment without mocks is correctly maintained, and the distinction between watchlist and non-watchlist symbols for leak testing demonstrates a strong understanding of the underlying codebase.

### 2. Strengths
- **Context Adherence:** Perfectly captures the exact testing criteria established in the context, including gap tolerance, environment switching, and dual-layer reconnection drops.
- **Nuanced Leak Testing:** Task 4 correctly identifies that watchlist assets use reference counting and stay subscribed, effectively planning the leak test around non-watchlist assets to prevent false negatives.
- **Proxy Leverage:** Task 2 cleverly utilizes the Vercel Proxy failure headers introduced in earlier phases to simulate true server-side disconnects rather than relying entirely on local client drops.
- **No-Mock Constraint:** The plan strictly respects the requirement to avoid local mocks, ensuring the integration with Capital.com is tested authentically.

### 3. Concerns
- **MEDIUM - Asserting Internal Errors in E2E:** Task 1 requires asserting that a `DataStitchingError` is thrown if the gap is > 1s. In Playwright E2E tests, internal JavaScript errors aren't always directly assertable unless they are exposed to the UI, explicitly caught by `page.on('pageerror', ...)`, or tracked via console logs. The plan lacks the mechanism for how Playwright will detect this internal state.
- **MEDIUM - Gap Recovery Behavior:** Task 1 tests that the system "fails appropriately" when the gap exceeds 1 second, but it doesn't specify testing the system's *recovery*. If a gap is too large, the expected behavior is likely a REST backfill/refetch rather than leaving the chart broken.
- **LOW - Post-Reconnect Data Gaps:** Task 2 verifies that the "UI updates correctly on tick after reconnection". However, if the connection dropped for 30 seconds, there is a 30-second data gap. The test should ideally verify that historical data is stitched back in to fill the disconnected period, not just that new ticks arrive.
- **LOW - Live Environment Rate Limits:** Since these tests hit the real Capital.com API instead of mocks, running this suite concurrently in CI could trigger rate limits or IP bans. 

### 4. Suggestions
- **Refine Task 1 Error Assertion:** Update the task to specify how Playwright will detect the `DataStitchingError` (e.g., listening to `console.error`, catching unhandled page errors, or asserting on a specific UI error boundary/toast).
- **Test Gap Recovery:** Expand Task 1 to include verifying that when a `DataStitchingError` occurs, the application correctly recovers by issuing a fresh REST request to backfill the missing candles.
- **Verify Backfill on Reconnect:** Update Task 2 to assert that upon successful reconnection, the chart does not just resume ticking, but also successfully fills any missing candles from the downtime period.
- **Playwright Concurrency Config:** Add a small note to the plan to ensure `market-data-stitching.spec.ts` configures tests to run serially (`test.describe.configure({ mode: 'serial' })`) to minimize the risk of rate-limiting from the Capital.com live endpoints.

### 5. Risk Assessment
**Risk Level: LOW**
The plan is structurally sound and ready for execution. The concerns raised are primarily minor refinements regarding how E2E assertions are captured and ensuring complete coverage of system recovery states, rather than foundational flaws in the approach. Implementing the suggestions will make the resulting test suite fully comprehensive.

## Cursor Review

### 1. Summary
The plan successfully details a rigorous E2E testing suite mapped precisely to the Phase 5.2 context and research artifacts. It directly addresses the technical decisions (D-01 through D-05) by explicitly specifying test environments (live demo endpoint without mocks), gap tolerance scenarios, WebSocket reconnection flows (both client and server-side), and correct validation patterns for subscription memory leaks. The tasks are logically separated, focused, and the acceptance criteria cleanly define the "done" state for each test scenario.

### 2. Strengths
- **Strict Constraint Adherence**: Explicitly enforces the project constraint to test against the live Vercel proxy rather than using local mocks (D-05), which will yield higher-confidence tests.
- **Nuanced State Awareness**: Captures the behavior of the `activeEpics` reference counting by correctly instructing the leak tests to use non-watchlist symbols, avoiding false negatives (D-03).
- **Comprehensive Resilience Coverage**: Addresses both client-side connection drops and server-side disconnect vectors via proxy failure headers (D-02).
- **Clear Error Assertions**: Includes the specific `DataStitchingError` assertion for gap tolerances >1s, aligning perfectly with the established engine requirements (D-01).

### 3. Concerns
- **Deterministic Gap Simulation (HIGH)**: Task 1 requires asserting that a gap >1s throws a `DataStitchingError`, but does not specify *how* to reliably force this gap against a live API. Doing this deterministically in a live E2E test without mocks requires precise network interception (e.g., intentionally delaying the WebSocket connection or the REST payload) which is highly prone to flakiness.
- **Visual State Assertions (MEDIUM)**: Task 3 asserts that the "UI visually retains old environment data until overwritten". Validating "smooth overwrites" visually or via raw DOM manipulation in E2E tests can be flaky if it relies on implicit timing rather than explicit state signals indicating when the data swap has securely completed.
- **Live Account State Pollution (LOW)**: Testing against a live demo endpoint always carries some risk of rate limiting or concurrent session interference if tests are run in parallel, though market data fetching is less destructive than order placement.

### 4. Suggestions
- **Refine Task 1 (Gap Simulation Strategy)**: Explicitly define the Playwright interception strategy for simulating the >1s gap. For example, instruct the implementer to use Playwright's `route.continue()` with deliberate delays on the WebSocket stream to intentionally drift the timestamps apart from the historical REST data.
- **Refine Task 3 (State-based Assertions)**: Change the acceptance criteria from "visually retains" to asserting on explicit state variables (e.g., `usePriceStore` states, checking that the price nodes in the DOM are never empty during the environment toggle).
- **Test Isolation**: Add explicit notes in the implementation plan to ensure these E2E tests are designed to run independently (e.g., proper setup and teardown of Playwright contexts) so they do not interfere with each other's WebSocket interceptions.

### 5. Risk Assessment
**MEDIUM**

**Justification:** While the test coverage strategy perfectly mirrors the project requirements, relying 100% on a live endpoint for testing precise timing conditions (like >1s data gaps) and server disconnects introduces a significant risk of test flakiness in the CI/CD pipeline. Playwright network interception is powerful, but mimicking race conditions against live sockets requires very meticulous implementation to avoid false failures. The plan is functionally correct but carries medium implementation risk.

## Consensus Summary

The reviewers agree that the plan is strong, accurately reflecting the strict "no mocks" project directives and mapping perfectly to the gap tolerance, reconnection, and leak prevention scenarios required by Phase 5.2. However, they uniformly highlight execution-level risks due to potential test flakiness when asserting precise timing constraints against a live endpoint.

### Agreed Strengths
- **Flawless Traceability:** Complete alignment with D-01 through D-05 requirements.
- **Watchlist Symbol Nuance:** Correctly identifies that non-watchlist symbols must be used to validate subscription drop logic.
- **Comprehensive Disconnect Vectors:** Robust testing strategy involving both client-side network interruptions and server-side proxy failure headers.

### Agreed Concerns
- **Deterministic Gap Simulation (HIGH)**: Without artificially delaying the live REST/WebSocket responses (via Playwright interception), enforcing a >1s gap deterministically is prone to severe CI flakiness.
- **E2E Internal Assertions (MEDIUM)**: Internal JavaScript errors like `DataStitchingError` cannot be natively asserted via the UI alone; explicit tracking mechanisms (`page.on('pageerror')` or console spy) are needed.
- **Concurrency & Rate Limit Risks (LOW)**: Hitting live Capital.com APIs might trigger IP rate limits if tests are run in parallel.

### Divergent Views
- **Scope of Gap Recovery Testing:** Codex emphasized verifying the *recovery* phase after a gap is triggered (e.g. issuing a fresh REST backfill), while Gemini focused purely on defining the UI's loading state. Codex also brought up testing the historical backfill *after* a long server drop in Task 2.
- **Implementation File Structure:** Gemini suggested splitting the complex E2E behaviors into two separate files (`market-data-stitching.spec.ts` and `market-data-resilience.spec.ts`) for maintainability, while the other reviewers did not address file bloat.
