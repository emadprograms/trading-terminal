# Phase 05.2 Research: Data Stitching Validation

## Objective
Answer: "What do I need to know to PLAN this phase well?"

To effectively plan **Phase 05.2: data-stitching-validation** (satisfying requirement **TEST-05**), the planner must account for the following technical decisions, existing codebase state, and testing guidelines.

## 1. Test Environment & Mocking Strategy (CRITICAL)
- **Target the Live Proxy:** All tests must run against the deployed live demo endpoint (via the Vercel proxy). **Do not use local mocks** (as per `REQUIREMENTS.md` "Out of Scope" and Context `D-05`). Mocks are considered unreliable for these tests.
- **Playwright Config:** Leverage the existing `playwright.config.ts` setup which includes mock-bypass headers and error injection headers.

## 2. Key Testing Scenarios to Plan For
The plan must break down implementation into tests covering these specific scenarios:
- **Gap Tolerance (D-01):** Validate the handover between the last REST candle and the first WebSocket tick. A lenient gap is allowed, but a gap of `>1s` should explicitly fail the test. Be aware that the `SyncCoordinator` handles gap validation and may throw a `DataStitchingError`.
- **Reconnection Resilience (D-02):**
  - *Client-side drops:* Simulate using Playwright network interception.
  - *Server-side disconnects:* Trigger using failure headers sent to the Vercel Proxy (introduced in Phase 5.1).
- **Subscription Leak Tracking (D-03):** 
  - Test for leak prevention by switching between non-watchlist assets and verifying that an `unsubscribe` WebSocket payload is transmitted.
  - *Watchlist caveat:* Symbols in the watchlist are intentionally kept active via reference counting (`activeEpics` Map in `src/lib/ws-manager.ts`). Tests must use symbols **not** in the watchlist to properly test for unsubscription leaks.
- **Environment Switching (D-04):** When switching between Demo and Live environments, assert that the old data remains visible on the chart until it is smoothly overwritten by the new live data.

## 3. Codebase Integration Points
The implementation tasks should target the following files and systems:
- **`tests/e2e/`**: New or modified test files dedicated to data stitching, leak tracking, and resilience.
- **`src/lib/ws-manager.ts`**: The core subject under test for subscription leaks (`activeEpics`) and WebSocket drops.
- **`SyncCoordinator`**: The core subject under test for REST/WS gap stitching and `DataStitchingError` assertions.

## 4. Planning Guidelines
Ensure the generated `PLAN.md` focuses strictly on the E2E testing validation suite. Tasks should be structured logically around the aforementioned scenarios (e.g., Task 1: Gap Tolerance & Stitching Tests, Task 2: Reconnection & Network Drops, Task 3: Subscription Leak Tracking, Task 4: Environment Switch State).
